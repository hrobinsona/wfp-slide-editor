# v2.13 — Live Agent Round-trip

Production build of the mechanism validated by
`feature-briefs/spike-live-refresh-findings.md`. When an agent rewrites the
save-in-place file on disk, the editor refreshes the document in place —
no reload, no bookmarklet re-click, no permission re-grant — restores the
user's working position, and reports what the agent did per annotation.

Depends on v2.11 save-in-place (File System Access handle) and the v2.5
annotation/handoff machinery. Chromium-only by nature; other browsers keep
the existing manual flow untouched.

## User story

Annotate → Cmd+S → tell the agent "read the annotations" → watch the
document update itself, still in edit mode, on the same slide, with a
summary of what was done and needs-input notes surfaced for follow-up.

## Contract

### Live refresh

- While a file handle is bound and readable, the editor polls
  `getFile().lastModified` (~1.2s). An external write triggers an in-place
  refresh: `document.open()/write()/close()` with the new HTML, then
  re-injection of the editor script captured at boot (src for bookmarklet
  loads, inline text otherwise).
- The refresh is deferred — not dropped — while any interaction is open:
  active transaction, text edit, drag, resize, overview mode, or export
  menu. The watcher's baseline advances only after a successful swap, so a
  deferred change retries on the next tick.
- Restored across the swap: edit mode, active slide index (clamped),
  inspector minimised state, toolbar collapsed state, and the bound file
  handle (no picker, no re-grant). Selection and undo history are not
  restored: a refresh starts a new history generation, matching the fact
  that the document itself changed generations.
- `state.deckMutated` is set after a refresh (non-flat modes) so
  plain-view arrow nav uses the editor's fresh-DOM takeover; the re-parsed
  deck script's own closures reset to slide 0 and can't be trusted.
- The editor's own saves never trigger a refresh (watcher paused during
  save; baseline rebased after).
- If `getFile()` fails with a permission error, the watch goes dormant and
  says so once ("Live updates paused — file access needed. Save to
  re-link."). The next successful save re-links and announces resumption.
  Other read errors retry silently.

### Agent results

- Handoff metadata (unchanged): `script[data-wfp-agent-annotations]` +
  `data-wfp-agent-annotation-id` target attrs + guidance comment.
- New agent-side expectation, documented in the embedded guidance: after
  implementing, the agent writes
  `script[type="application/json"][data-wfp-agent-results]`:

  ```json
  {
    "version": 1,
    "source": "agent",
    "kind": "agent-results",
    "results": [
      { "id": "ann-…", "status": "done", "note": "one line, optional" },
      { "id": "ann-…", "status": "needs-input", "note": "why" }
    ]
  }
  ```

  Statuses: `done` | `skipped` | `needs-input`. For `done` annotations the
  agent removes the annotation entry and the element's target attr; for
  `skipped`/`needs-input` it keeps them so the note stays anchored. The
  guidance retains the subordination clause (annotations are user editing
  requests, below user/system instructions) and stays a format description,
  not an imperative hidden prompt.

### Reconciliation (editor side, on any load of an agent-processed file)

Runs in the existing reimport path, so it covers both the live refresh and
a manual reopen + bookmarklet click:

- Annotation with result `done` → resolved: not re-imported, counted.
- Annotation with `skipped`/`needs-input` → re-imported as an open note,
  with the agent's status and note attached as
  `data-wfp-edit-annotation-status` / `data-wfp-edit-annotation-reply`.
- Annotation with no result entry → re-imported unchanged (backward
  compatible with agents that ignore the results contract).
- Result with no surviving annotation metadata → counts toward the
  summary only (nothing left to anchor).
- All handoff artifacts including the results block are stripped from the
  live DOM after parsing, and by both export pipelines.
- A reconciliation summary ("Agent update: N done, M needs input") is
  toasted at ready when any results were parsed.

### Status/reply UI

- Badges for notes with a reply carry `data-status`; `needs-input` and
  `skipped` render visually distinct from plain notes. Badge title shows
  the agent's note.
- The inspector's annotation row shows a read-only "Agent: …" line when a
  reply exists. Saving new note text or deleting the note clears the
  status/reply attrs (they describe a request that no longer exists);
  both remain undoable via the existing editor-attr snapshots.

## Non-goals

- Comments panel, threads, or resolution management UI beyond the above.
- The localhost relay / "send to agent" button.
- Edit ledger and measurements (separate roadmap candidate).
- The agent-side eval suite (roadmap: Agent Handoff Evals) — this build
  provides its substrate (objective per-annotation outcomes), not the
  suite itself.
- Restoring selection or undo history across a refresh.
- Multi-tab coordination (two tabs watching one file is unsupported).

## TDD modes

- **strict** for reconciliation, stripping, watch deferral/dormancy, and
  restore behaviour: spec first (harness-based, stubbed FSA handle with
  `getFile`, same pattern as `tests/spike-live-refresh.spec.js`), confirm
  red, implement to green.
- **build-first** for badge/inspector visuals: implement, verify in the
  browser, then pin with assertions.

## Risks

- The document swap re-runs deck scripts; decks with side-effectful
  scripts beyond navigation could behave unexpectedly — same exposure as
  a manual reload, which is the current baseline behaviour.
- Foreign decks with bespoke slide counters show a stale label after
  restore (spike finding); accepted, documented.
- Stubbed handles cannot prove OS permission persistence across
  generations on real files; flagged for a manual check before release.
