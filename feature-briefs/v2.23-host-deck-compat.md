# v2.23 — Host Deck Compatibility: active-class token + pointer navigation

**Status:** built, tests green (branch `fix/host-deck-active-class-and-pointer-nav`)
**TDD mode:** strict — this is selection logic and export behaviour, not a visual surface
**Depends on:** deck-root resolution (native / foreign / flat), overview mode, export normalisation

## Problem

A deck produced by a newer generator (`pelvic-floor-confidence.html`) loads the editor
fine and toggles into edit mode, but nothing on the slide can be selected. Clicking
anywhere just pages the deck. Two independent defects, both in the editor:

**1. The active-slide token is an authoring choice, and we hardcoded one of them.**

The deck marks its visible slide `is-active`:

```js
slides.forEach((slide, i) => slide.classList.toggle("is-active", i === current));
```

`getActiveSlide()` matches `classList.contains('active')` exactly, so it returns `null`,
`findSelectableTarget()` rejects every click, and the fourteen call sites that depend on
an active slide — selection, drag, resize, text edit, notes, overview — all go dead.

**2. The deck navigates on `pointerup`, which fires before `click`.**

```js
deck.addEventListener("pointerup", (event) => {
  if (event.button !== 0) return;
  showSlide(event.clientX < window.innerWidth / 2 ? current - 1 : current + 1);
});
```

Every guard the editor owns — `onClick`, `state.suppressClickUntil` — is keyed to `click`
and `mouseup`. None of them can observe a `pointerup`. By the time `onClick` runs the
slide has already changed, so the clicked element no longer belongs to the active slide.

Defect 2 dominates defect 1: fixing the token alone changes nothing observable, because
the slide still flips out from under the click. Both must land together.

Every deck the editor was built against binds click only to nav dots
(`dot.addEventListener('click', () => this.goTo(i))`), never to the deck or document,
which is why neither defect has surfaced before.

## Knock-on damage

- **Overview mode diverges silently.** `synchronizeSlideState()` writes `active`; the deck
  keeps rendering from `is-active`. Clicking thumbnail 4 leaves the editor believing it is
  on slide 3 while the deck still shows slide 0.
- **Export leaves residue.** `normalizeExportStartupState()` stamps `active` on slide 0 and
  never clears `is-active`. The exported file opens on the right slide only because the
  deck's own script re-runs `showSlide(0)` at load — the editor's "export starts on slide 1"
  contract is not actually being honoured.

### Found during implementation — a third defect

The regression fixture reproduces the real deck's shape faithfully, including
its wrapper: `<main class="stage"><section class="deck">`. That exposed a third,
independent break the original diagnosis had not reached.

Overview mode hides every body-level sibling of the deck root, so that progress
dots and nav hints (which WFP decks mount as body children) do not overlay the
grid:

```css
body[data-wfp-edit-overview="on"] > *:not([data-wfp-edit-deck-root]):not(#wfp-editor-root) {
  display: none !important;
}
```

Every deck the editor grew up with mounts `.deck` straight into `<body>`, so the
deck root itself always matched the exception. A deck that wraps its canvas has
the wrapper caught by this rule instead — confirmed on the real deck, where
`main.stage` computed to `display: none`, the deck root collapsed to 0x0, and
overview rendered blank with zero-sized thumbnails.

Fix: mark the chain between deck root and `<body>` with
`data-wfp-edit-deck-ancestor` at resolution time, spare those elements from the
hide rule, and give them `display: contents` while overview is on so the
wrapper's fixed-canvas sizing stops constraining the reflowed grid. The marker
is swept by the existing `data-wfp-edit-*` export cleanup.

## Verified not at fault

Checked and cleared, so they stay out of scope:

- Deck scale. `DOMMatrixReadOnly(t).a` correctly yields `0.75` from
  `translate(0px, 45px) scale(0.75)`; the translate does not contaminate the `a` component.
- Keyboard. The deck binds `f`, arrows, Space, PageUp/Down, Home/End on `document`, but
  `isTypingTarget` and the text-edit branch already contain them. No leakage observed from
  inspector inputs.
- Flow unlock. First drag unlocks without moving, identical to the control fixture.
- Export hygiene. No editor markers and no `#wfp-editor-root` in the output.

## Fix

### Part A — resolve the active-class token once, route every read and write through it

Add `resolveActiveClass()` beside the existing native/foreign/flat resolution in
`resolveDeckRoot()`, and carry the result on `deckContext`.

```
candidates: ['active', 'is-active']  (in order)
pick the first token carried by exactly one direct-child slide
no match, no slides, or flat mode -> 'active'
window.__WFP_ACTIVE_CLASS__ overrides, mirroring __WFP_EDIT_ROOT__
```

`'active'` is probed first so a deck carrying both keeps its legacy meaning. Detection runs
once at bootstrap: real decks activate a slide synchronously before the bookmarklet lands,
and a deck with no active slide at injection time has nothing to detect anyway.

Expose two helpers and replace the fifteen slide-level call sites:

```js
function isActiveSlide(el)       // read
function setSlideActive(el, on)  // write
```

Sites: `40-helpers-selection-inspector.js` (`getActiveSlide`), `50-history.js` (slide
insert/delete undo and redo), `60-modes-overview-keyboard.js` (thumb state,
`synchronizeSlideState`, `navigateRelativeInDeck`, slide delete),
`95-export.js` (`normalizeExportStartupState`), `96-live-refresh.js` (slide index).

**Do not blanket-replace the string `'active'`.** Two sites —
`60-modes-overview-keyboard.js` and `95-export.js` — write `.progress-dot.active`, a
separate host convention that is unrelated to slide visibility and must stay literal.

### Part B — take the pointer gesture from the host while the editor owns the canvas

A capture-phase suppressor on `document` for `pointerdown`, `pointerup`, `pointercancel`
and `click`, active only while `state.editMode || state.overviewMode`, skipping anything
inside the editor root.

- `stopPropagation()` only. `preventDefault()` would break focus and the contenteditable
  caret during text edit.
- Not `stopImmediatePropagation()`. The editor's own document-level listeners are
  registered on the same node and must still run.
- `click` is included alongside the pointer events so a deck that pages on `click` rather
  than `pointerup` is covered by the same mechanism.

This mirrors the keyboard takeover already described in the project gotchas: editor-owned
input runs in capture phase and stops propagation when edit or overview mode owns it.

**Accepted behaviour change:** slide content that is genuinely interactive in the host page
goes inert while edit mode is on, for every deck, not just this one. That is the intended
reading of edit mode — the editor owns the canvas — but it is a change to existing decks
and is called out here deliberately.

### Part C — a committable regression fixture

The deck that exposed this is real Philips product strategy and cannot enter `fixtures/`.
Add a sanitized synthetic deck modelled on the allow-listed `fixtures/foreign-deck.html`,
carrying only the two traits under test: `is-active` visibility and `pointerup` half-screen
navigation. Allow-list it in `.gitignore` alongside the other two.

## Tests

Strict TDD — each of these is written and seen failing before the corresponding change.

Against the new fixture:

1. An element on the visible slide selects on click in edit mode.
2. An edit-mode click does not advance the deck.
3. With edit mode off, a click still advances the deck (presenting is unaffected).
4. An overview thumbnail click changes the *visible* slide, not just the editor's belief.
5. Export normalises to the first slide using the deck's own token, leaving no foreign
   `active` residue.

6. The deck still has layout in overview mode, and every thumbnail is
   genuinely clickable rather than zero-sized.
7. The `data-wfp-edit-deck-ancestor` marker never reaches the export.

Against the existing `.active` fixtures:

8. Selection, overview navigation and export are unchanged.

### Test harness

The harness carried the same token-blindness as the editor, which mattered
because the rotation pool exists precisely to run the end-to-end suites against
decks the editor did not grow up with. `_helpers.js` gains `activeClassToken()`
and `ACTIVE_SLIDE_SELECTOR`; `waitForSlideSettled`, `activateSlide`,
`activeSlideIndex` and `collectTargetCandidates` now resolve the deck's token
rather than assuming `active`, as do the three rotation specs
(`09-end-to-end`, `v2-1-6-end-to-end`, `v2-8-end-to-end`). The new fixture
therefore joins the rotation pool as real coverage instead of being excluded
from it.

## Result

580 tests: 577–578 passing, 2 skipped (uninstalled private fixtures). The
existing 566 tests pass with the change applied, matching the pre-change
baseline exactly.

A full parallel run fails by roughly one test, and a *different* one each time
— observed in `v2-17-bring-to-front` (three separate tests) and
`v2-21-notes-panel`. Every one passes in isolation and under `--repeat-each`.
Confirmed pre-existing: a clean-baseline run with none of this work applied
reproduces it too. This is ambient parallel-suite flakiness, not a property of
any one spec. Tracked separately; not addressed here.

## Out of scope

- Teaching the editor any other host navigation convention (scroll snap, hash routing,
  `<details>` decks). The token resolver and the gesture suppressor are the two seams; new
  conventions extend those rather than adding new special cases.
- Re-detecting the active token after bootstrap.
- The `.progress-dot.active` convention, which is left literal on purpose.
