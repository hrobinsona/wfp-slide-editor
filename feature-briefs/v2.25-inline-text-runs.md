# v2.25 — Inline formatting runs are text, not boxes

**Status:** built, tests green (branch `claude/pensive-ride-l0ifc6`)
**TDD mode:** strict — selection resolution, verified by ring geometry and inline style
**Depends on:** inline text edit (Phase 7), flow unlock (`unlockToAbsolute`)

## Problem

Bolding a few words of a paragraph made "a new text box" appear and shifted
the words around it.

Cmd/Ctrl+B while inline-editing is handed to the browser, whose native bold
wraps the selection in `<b>`. That is fine and exports cleanly. The defect
was in what happened next: `findSelectableTarget()` returned whatever element
was clicked, so the next click on the bold words selected the `<b>` itself —
a selection ring around one run of text, its own Position/Size readouts, and
a drag that ran `unlockToAbsolute` on it. The run became `position: absolute`
inside the paragraph and the paragraph was dimension-pinned around the hole
it left, so the neighbouring words reflowed.

Reproduced on `fixtures/pointer-nav-deck.html`: after Ctrl+B the ring on the
bold word measured 148×33 against the paragraph's 750×76, and a 20px drag
wrote `position: absolute; left; top; width; height` plus
`data-wfp-edit-frozen` onto the `<b>` and `width/height` onto the `<p>`.

## Decision

A run of inline formatting that sits among a block's own text is part of
that text. `findSelectableTarget()`:

1. walks up through every ancestor whose computed display is `inline` (not
   inline-block, not a flex/grid item — those are boxes an author placed),
   so a run inside a run — `<span style="color"><b>…</b></span>`, exactly
   what colouring then bolding a phrase produces — is still one run;
2. decides at the first non-inline ancestor: if it carries text nodes of its
   own (`isTextBearing`) the chain is mixed into its text and that block is
   the target; otherwise the outermost run is a box the author placed and is
   selected as before.

Replaced elements (`<img>`, inline `<svg>`, `<video>`, `<canvas>`,
`<iframe>`…) compute to `display: inline` too, but they are boxes the user
moves and resizes, so they never climb.

So `<strong><em>…</em></strong>` inside a paragraph resolves to the
paragraph, a `<b>` inside a `<span class="chip">` resolves to the chip, a
lone `<strong>` stat inside a whitespace-only card is unchanged, and an icon
`<img>` mid-sentence is still selectable on its own. A block whose entire
content is one run (`<p><b>all bold</b></p>`) still selects the run — the
parent has no text of its own — which is the pre-existing behaviour and out
of scope here.

All three gesture entry points share the resolver — click (selection),
mousedown (drag) and double-click (text edit) — so bold words now select,
move and edit as their paragraph.

## Out of scope

- An editor-owned bold control. The native shortcut already does the right
  thing to the DOM; only the selection model was wrong.
- The second report received alongside this one (deleting the first character
  of a bullet deletes the bullet) — not reproducible on the public fixtures,
  tracked in `FEATURES-AND-BUGS.md` pending real markup.

## Tests

`tests/v2-25-inline-text-runs.spec.js` — click on a Ctrl+B word selects the
paragraph; dragging the bold word of an in-flow paragraph unlocks the
paragraph (sibling pinned in place) and leaves the `<b>` unstyled and
unpinned; double-click edits the paragraph; nested runs and a colour-span
wrapped run climb to the paragraph, a run inside a chip resolves to the
chip, and an inline `<img>` among text stays selectable.
