# v2.17.1 — Front: fix stacking scope (bug fix)

**Status:** planned
**TDD mode:** strict (reproduce each failure as a failing test first, then implement)
**Supersedes:** the "stacking scope = siblings" decision in `v2.17-bring-to-front.md`. That decision was wrong; this brief is the corrected contract.

## The bug (user-reported, reproduced)

Front frequently does nothing on real decks. Reproduced against shipped `editor.js` with three minimal cases (probe script: see Repro section):

- **B — cross-container z:** competitor lives in a later sibling *container* carrying `z-index: 5`. Sibling scan sees no competitors → writes `z-index: 1` → element stays behind.
- **C — stacking-context cap:** the selected element's ancestor has a `transform` (WFP decks do this constantly — entrance animations). The ancestor becomes a stacking context; no z-index on the child can escape it. Front writes a z that cannot matter.
- **D — non-sibling flat competitor:** overlapping element elsewhere in the slide with `z-index: 2`. Sibling-derived plan writes `1` → stays behind.

Root cause: v2.17 computed the required z from `parentElement`'s children. CSS z-order competes within the nearest stacking-context ancestor and is capped by every intermediate stacking context — sibling scope is simply the wrong model.

## Corrected contract

"Bring to front" must make the selected element **actually paint above every element it visually overlaps within the active slide**, verified by paint truth (`elementsFromPoint`), not inferred from z values.

## Algorithm

`computeFrontPlan(targets)` / `applyFrontPlan` replace the sibling-scope helpers (`siblingMaxZIndex` etc. — remove or rewrite; do not leave dead code):

1. **Competitor set** (per target): every element in the active slide's subtree whose viewport rect (`getBoundingClientRect`) intersects the target's rect with positive area — excluding the target, its ancestors, its descendants, all co-targets and their descendants, and non-painted elements (zero-area rects). Rects are compared in viewport space only — no style writes come from them, so **no scale division is involved** (division by `getCanvasScale()` applies only when converting pointer deltas to style pixels, which this feature never does).
2. **Required z:** `max` over all targets' competitors of `chainMaxZ(competitor)` = the max numeric `z-index` among the competitor and its ancestors strictly below the slide (auto/static → 0).
3. **Assign:** process targets in current stack order (existing `compareStackOrder`); target *i* gets `required + 1 + i`. Static targets get the existing `position: relative` fix-up. Every write: `touchElement` first, inside the one txn.
4. **Verify & climb (the C fix):** after assignment, for each target × still-overlapping competitor, sample the intersection rect (centre + 4 quarter points) with `document.elementsFromPoint`, skipping editor-root nodes. If any competitor (or its descendant) still paints above the target (and no target-or-descendant hit above it): find the target's nearest ancestor **strictly below the slide** that establishes a stacking context, write `required + 1 + i` z onto it too (static fix-up if needed, `touchElement` first, dedupe ancestor writes across targets by element keeping the max), and re-verify. Climb to the next capping ancestor if still occluded; stop at the slide. The loop is bounded by ancestor depth.
   - Stacking-context test (pragmatic, commented): positioned with non-auto z-index; `transform`/`filter`/`perspective`/`clip-path` ≠ none; `opacity < 1`; `will-change` containing transform/opacity; `isolation: isolate`; `mix-blend-mode` ≠ normal; `contain` with layout/paint/strict/content.
   - Raising an ancestor brings that container's subtree forward — intended and unavoidable; it is what "in front" means for a nested element. State this in a code comment.
5. **No-op guard becomes paint-truth:** before opening a txn, run the verification sampling; if every target already paints above all its competitors at every sampled point, return — no txn, no writes, no history entry. (Replaces the old z-comparison guard.)
6. **Repeat-click stability:** because co-targets are excluded from each other's competitor sets and the guard is paint-truth, a second click must produce zero writes and zero history entries — including for multi-target plans.

`elementFromPoint` caveat: elements with `pointer-events: none` are invisible to sampling (the editor's own ring already relies on this). Acceptable known edge; do not try to compensate.

## Non-goals

- Send to back / explicit z management UI.
- Reparenting or DOM reordering.
- Cross-slide or editor-chrome stacking.

## Accepted implementation divergences (recorded post-review)

- **No-op guard is paint-truth AND z-plan conjunction**, not pure paint truth: a pure paint check makes Front a silent no-op for any element with no overlapping competitor, regressing the original v2.17 sibling contract. Paint truth remains the decisive test where they disagree.
- **Competitor exclusions extend to co-targets' ancestors** — required for multi-target repeat-click stability (an ancestor raised by one target's climb must not become another target's competitor).
- **The climb refuses to promote static ancestors whose stacking context comes from `opacity`/`isolation`/`mix-blend-mode`/`will-change: opacity`** (stacking-context triggers that are not containing-block triggers): promoting them to `position: relative` re-anchors their absolutely-positioned descendants and relays out the deck. Front may leave that narrow occlusion shape unresolved instead of silently moving content.
- `position: fixed|sticky` added to the stacking-context test (always create one).
- **Paint truth outranks relative target order when containers conflict** (recorded with the v2.18.1 C1 convergence fix). Step 3's "keep the targets' relative order" holds for the z *assignment* in every case, but two targets in different stacking-context containers can only keep their relative *paint* order if the containers allow it: if freeing target A requires A's container to out-stack B's container, A's whole container — B included — moves above B. Step 4 is decisive, so paint truth wins and the pair's order flips. Flat (same-context) targets are unaffected.
- **A mutual occlusion cycle never reaches a no-op** (pre-existing, restated here): if freeing A re-buries B and freeing B re-buries A, no assignment satisfies the paint-truth guard, so every click writes and pushes an entry. The convergence loop stops as soon as a pass fails to shrink the occluded set, which keeps the per-click growth to the same order as the pre-v2.18.1 single sweep, but it cannot make such a click silent.
