# v2.26 — Formatting inside a flex bullet keeps one text run

**Status:** built, tests green (branch `claude/pensive-ride-l0ifc6`)
**TDD mode:** strict — layout outcome verified by text line boxes, markup by innerHTML
**Depends on:** inline text edit (Phase 7), v2.25 (inline runs resolve to their block)

## Problem

v2.25 shipped and the user reproduced the original report immediately:
bold "Rethink" in a bullet and the rest of the sentence sits beside it in a
second column, wrapping under itself instead of under the bullet.

v2.25 fixed a real defect — the `<b>` selecting and dragging as a box — but
the screenshot is a different mechanism. The bullet is
`li { display: flex; gap }` with a `::before` dot, the shape WFP decks use.
Its text is one anonymous flex item. Cmd/Ctrl+B during the edit is the
browser's native bold and wraps the word in `<b>`; in a flex container every
element child is a flex item, so the DOM is now two items laid out side by
side. The `<b>` computes to `display: block` (blockified), which is also why
v2.25's inline-run climb did not apply to it.

Reproduced on `fixtures/pointer-nav-deck.html` with an injected flex
`<li>`: before, both text lines start at the bullet's x (97); after bold the
second line starts at 188, to the right of the bold word. The same bold in a
block-flow `<li>` wraps back to the left edge.

## Decision

The host, not the resolver, is the right place: the browser will keep
inserting elements for B/I/U and paste, and any element child of a flex
host is an item. So for the duration of an edit on a flex/grid host,
`startTextEdit` wraps each run of text nodes in a
`<span data-wfp-edit-text-run>`. The span is the flex item; whatever the
browser inserts lands inline inside it.

`endTextEdit` then removes any wrapper still holding only text nodes
(normalising the text nodes typing split), so an edit that only typed
leaves the markup exactly as authored; a wrapper holding formatting stays,
marker included, because the layout needs it —
`<li><span data-wfp-text-run="true"><b>Rethink</b> the whole…</span></li>`.

The marker is deliberately outside the `data-wfp-edit-*` namespace that
export sweeps (constant in `00-preamble.js`): it is structural markup the
deck now depends on, not editor state, and the editor must recognise it on
the next load. Two consequences follow, both raised in review of the first
cut:

- `isTextBearing` counts a wrapper as the host's own text. Every inspector
  text control (font size ± / typed / scrub, weight, align, text colour,
  row visibility) is gated on it, and moving the host's text nodes into the
  wrapper had silently switched them all off for the duration of the edit.
- `findSelectableTarget` resolves a wrapper to its host, so clicking the
  bold word afterwards selects the bullet, and double-clicking it edits the
  bullet, not the wrapper.

History is wrapper-neutral. The wrap happens after `touchElement` takes the
"before" snapshot and before the caret is placed; the unwrap happens before
`endTxn` takes the "after". But an inspector commit mid-edit goes through
`startInspectorTxn`/`endInspectorTxn`, which end and reopen the text-edit
transaction while the wrappers are installed — so `snapshotElement` now
serialises through `textRunNeutralHtml` (a clone with plain wrappers
removed). An untouched edit records no entry, a mid-edit inspector commit
records exactly its own entry, and undo of a bold restores the pristine
markup.

This is a deliberate, scoped exception to "editor-injected DOM lives inside
`#wfp-editor-root`": the wrapper has to sit in slide content to affect
layout, and a formatted edit permanently adds an author-visible `<span>`,
which author structural selectors (`li > span`, `:first-child`) can match.

Runs are bounded by element children: a `<span class="dot">` or icon the
author placed keeps its own item and is never merged into the text.
Whitespace-only runs (pretty-printed markup between elements) are skipped —
an anonymous item is not generated for them, so a wrapper would add a gap.

## Out of scope

- Editor-owned bold/italic controls. Native shortcuts do the right thing to
  the text; only the host layout needed protecting.
- Bullets already damaged by the bug in saved decks: they carry a `<b>` as a
  direct flex child. Editing such a bullet again does not merge the `<b>`
  back into the run (element children bound runs by design); the user
  re-applies the bold after undoing it.

## Tests

`tests/v2-26-flex-text-runs.spec.js` — bold in a flex bullet keeps the
second line at the bullet's edge, the `<b>` inline inside one item, the
kept wrapper marked and no edit marker or contenteditable left; a
typing-only edit leaves no wrapper; an untouched edit is byte-identical and
records no history (one undo reaches the edit before it); the inspector's
Bold segment applies to the host mid-edit and records exactly one
wrapper-free entry; clicking the bold word afterwards selects the bullet
and double-clicking edits it; export keeps the wrapper and sweeps every
`data-wfp-edit-*` marker; an author dot element keeps its own item; a
block-flow bullet is never wrapped; undo after bold restores the original
markup.
