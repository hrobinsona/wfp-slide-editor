# v2.22 — Markdown Review Mode

**Status:** built, awaiting review (branch `worktree-markdown-review-mode`)
**TDD mode:** build-first for the host page and editor gating; strict for `render.js` / `writeback.js` (pure functions — spec them directly in Node)
**Depends on:** v2.5 (annotations), v2.21 (notes panel), flat-document mode

## Goal

Annotate Markdown files with the existing editor. Markdown stays the source of truth: a `.md` file is rendered to HTML as a *working surface*, annotated with the normal annotation flow and the v2.21 notes panel, and saved back as **Markdown** — never as HTML.

Notes persist in the file as Obsidian callouts:

```markdown
> [!HARRY] this figure is from the old model
```

They render natively in Obsidian, grep cleanly, and need no handoff protocol at all — Claude Code opens the file, sees the callout, and acts on it. The file *is* the channel.

## Architecture

**No server.** Everything runs from a static host page (`tools/md-review.html`) opened over `file://`, using the File System Access API the editor already depends on:

- `95-export.js` already proves `showSaveFilePicker` works on `file://` origins.
- `96-live-refresh.js` already watches files by polling `handle.getFile().lastModified` — no HTTP anywhere.

**The editor stays Markdown-ignorant.** All Markdown knowledge lives in two pure modules the host page imports. The editor gains only two things: a mode flag that reduces its surface, and a *save sink* it calls instead of writing HTML.

**The source text is the source of truth; the DOM is a projection.** The host page holds the original Markdown string. Saving never serializes the DOM back to Markdown — it splices lines into the retained string at line numbers the renderer recorded. There is no HTML→Markdown conversion anywhere in the system.

**Anchoring is exact, not heuristic.** The renderer stamps `data-md-line` / `data-md-end` (0-indexed, inclusive) on every block. An annotation on a block therefore maps to a known source line range. No quote matching, no orphan class of bugs.

## Round trip

1. **Render:** `renderMarkdown(text)` → HTML with per-block source ranges. Existing `> [!HARRY]` callouts are *not* rendered as content; they are parsed out and re-attached as annotations (`data-wfp-edit-annotation-*`) on the block they follow, with the callout's own source range recorded on the element.
2. **Annotate:** normal editor flow. The notes panel lists every note in the file.
3. **Save:** `applyMarkdownWriteback(source, notes, edits)` diffs current annotations against the callouts that were in the file, emits insert/update/delete operations, applies them in **descending line order** so earlier line numbers stay valid, and returns new Markdown.

An agent that resolves a note deletes the callout; the next render simply shows no annotation there. An agent that needs input keeps the callout and appends a `> reply:` line, which renders back as the annotation's reply.

## Scope

**In:**
- Annotations (create, edit, delete) round-tripping as callouts — the primary goal.
- Text edits for **paragraphs and headings only**, preserving the heading's `#` prefix.
- Reduced editor surface in Markdown mode.

**Out (deliberate):**
- Geometry editing of any kind. Drag, resize, position/size, colour, opacity, and typography are meaningless on Markdown and are gated off — an inline `left:` on a paragraph has no Markdown representation.
- Text edits to lists, tables, code fences, and any block containing inline markup (links, bold, code). Replacing those lines from `textContent` would silently destroy syntax. Such blocks are left untouched and reported in the save toast.
- Obsidian-specific syntax fidelity: `[[wikilinks]]`, embeds, and Dataview render as literal text. This is an anchoring surface, not an Obsidian replica.
- Obsidian rendering fidelity (see above).

**Added after first review:**
- Edit mode is entered automatically — unlike a deck, this surface has no viewing use.
- `showDirectoryPicker` on the vault/repo root: a file list for one-click switching, and relative images resolved through the folder handle as blob URLs. The single-file picker remains for one-offs; both handles persist and reappear as Reopen buttons.

## Contracts

**Callout form.** `> [!HARRY] <instruction>`, continuation lines `> <more text>`, optional `> reply: <agent reply>` and `> status: needs-input|skipped`. The marker type is a constant (`MD_NOTE_TYPE`) so it can be renamed in one place.

**Placement.** A callout annotates the block that **precedes** it, and is written immediately after that block's last line. A callout with no preceding block attaches to the following one.

**Identity.** Callouts carry no ids in the file — that would be noise in a human-readable vault. Identity is positional: a note is matched to its source callout by the callout's line range, captured at render.

## Files

- `src/md/render.js` — Markdown → HTML with source ranges; callout extraction.
- `src/md/writeback.js` — annotation/edit diff → new Markdown.
- `tools/md-review.html` — static host page: file picker, render target, save, editor injection.
- `src/editor/20-dom-css.js`, `30-ui-inspector-controls.js`, `40-helpers-selection-inspector.js` — Markdown-mode gating and the save sink.
- `tests/v2-22-markdown-review.spec.js` — pure-function specs plus an end-to-end host-page pass.

## Verification

`render → annotate → writeback → re-render` must be a fixed point: the re-rendered annotation set equals what was saved. Insertion of multiple notes in one save must not corrupt line numbers. A file with no notes must round-trip byte-identically.
