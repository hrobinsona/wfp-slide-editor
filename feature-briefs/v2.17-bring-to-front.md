# v2.17 — Bring to Front

**Status:** planned
**TDD mode:** strict (logic + export behaviour; write the Playwright spec first, confirm it fails, then implement)

## Goal

Let the user raise the selected element above overlapping siblings: a **Front** action button in the inspector that bumps the element's `z-index` above every sibling in its stacking scope. One-way only — no "send to back", no full z-order manager (see Non-goals).

## Product decisions

- **Placement:** a `Front` button in the existing inspector action row, alongside Reset / Duplicate / Delete. Same `wfpe-action-btn` pattern (`dataset.action = 'bring-to-front'`), new stacked-layers SVG in `ICONS`.
- **Stacking scope:** the element's siblings (element children of its `parentElement`). That matches how z-index actually competes in CSS and how WFP decks lay out overlapping elements (absolutely-positioned children of the slide). We do NOT try to out-stack elements in other stacking contexts.
- **Static elements:** `z-index` is inert on `position: static`. If the computed position is `static`, also set `position: relative` (no layout shift) so the bump takes effect. This mirrors what drag/unlock already does conceptually (style writes that make the element independently paintable).
- **Multi-select:** apply to all of `state.selectedElements`, preserving their current relative stacking order (sort by effective z-index then DOM order; assign `maxZ + 1`, `maxZ + 2`, …).
- **No-op guard:** if the element is already the sole front-most among its siblings, do nothing — no style write, no history entry, no z-index inflation on repeated clicks.
- **z computation:** effective z of a sibling = `parseInt(getComputedStyle(sib).zIndex)` when numeric, else treated as 0 (`auto`). New value = max + 1. A value of ≥1 wins over all `auto` positioned siblings regardless of DOM order, which is the intent.

## Non-goals

- Send to back / step forward / step backward (trivial follow-ups if wanted; tracked in ROADMAP if requested).
- Reordering DOM position. This is a pure inline-style change — export cleanliness and undo depend on that.
- Cross-stacking-context arbitration (e.g. out-stacking an ancestor's sibling).

## Implementation sketch

1. **`src/editor/30-ui-inspector-controls.js`**
   - Add `ICONS.layers` (simple two-stacked-squares SVG, match existing icon style/size).
   - Build the `Front` button next to `resetBtn` in the action row; include it in the same mode/feature gating as the other action buttons (check `applyModeFeatureGating()` and disabled-state handling for Reset/Duplicate — mirror it).
   - Click handler modelled on `resetBtn`'s:
     ```js
     const ctx = startInspectorTxn();
     for (each target) { touchElement(el); /* position fix-up + zIndex write */ }
     endInspectorTxn(ctx);
     refreshSelection();
     ```
   - Guard first (before opening a txn): no selection → return; already sole-front → return.
2. **Helper** — put the "compute sibling max z / assign new values" logic in a small named function near the other selection helpers (`40-helpers-selection-inspector.js`) if it doesn't read cleanly inline; prefer whichever the surrounding code style supports. Small functions, no classes.
3. **Build:** edit fragments only, then `npm run build:editor`. Never hand-edit `editor.js`. Tests load the built `editor.js`, so rebuild before every test run.
4. **Export:** no changes expected — export already strips only `data-wfp-edit-*` / `contenteditable` / editor DOM; inline `z-index` and `position` persist. Covered by test, not code.

## Test plan — `tests/v2-17-bring-to-front.spec.js`

Use `fixtures/foreign-deck.html` (sanitized, present on this machine — private fixtures are NOT available locally; do not reference them). Model helpers/setup on `tests/v2-15-unlock-hardening.spec.js` / `tests/_helpers.js`.

1. **Basic raise:** two overlapping absolutely-positioned siblings; select the one underneath, click Front → its computed z-index exceeds the sibling's, and `document.elementFromPoint` at an overlap point returns it (or a descendant of it).
2. **Static element:** select a static element, click Front → computed position becomes `relative`, z-index set; element's layout box (rect) unchanged.
3. **No-op repeat:** click Front twice; a single undo returns the element to its pre-click inline style (proves the second click pushed no history entry).
4. **Undo/redo:** after Front, undo restores the original inline style (no stray `z-index`/`position`), redo reapplies both.
5. **Multi-select (if selection helpers make it cheap):** two selected elements keep their relative order but both end above an unselected overlapping sibling.
6. **Export cleanliness:** after Front, exported HTML retains the `z-index` inline style and contains no `data-wfp-edit-*`, `contenteditable`, or `#wfp-editor-root` remnants.

## Gotchas (from CLAUDE.md — all apply here)

- `editor.js` is generated; `npm run build:bookmarklet` enforces sync — run `npm run build:editor` after fragment edits.
- Undo/redo must not leave `state.selected` pointing at detached DOM (not expected here — no DOM moves — but keep it in mind).
- Editor markers must never leak into exported HTML.
- Only `.slide.active` is visible; operate on the active slide's selection only (selection state already guarantees this).
- Do not alter fixture rendering when the editor is not loaded (we only write inline styles at user action time).
